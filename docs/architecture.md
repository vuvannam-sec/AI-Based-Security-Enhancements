# Architecture

## Purpose

AI-Based Security Enhancements is a single-host research pipeline for studying how operating-system telemetry, simple learned classifiers, explicit rules, and response primitives can be connected safely enough for a lab environment.

It deliberately separates observation from enforcement. The Sensor and ML service can inspect or classify events without privileged process-control access; the Enforcer owns the privileged operations.

## Components

### Sensor

The Sensor polls `/proc`, normalizes process observations, maintains a bounded in-memory event buffer, and can export events to CSV. When automatic detection is enabled, it performs a cheap pre-filter before submitting suspicious events to the detection worker pool.

The pre-filter exists to avoid sending every sampled process to the ML service. It considers sustained resource use and a small set of security-relevant file, path, and network indicators.

### ML service

The ML service trains and loads a RandomForest classifier. Training data is generated locally by the project and is intentionally treated as demonstration data. Feature engineering combines numeric process measurements with derived binary signals such as sensitive-path access and suspicious execution location.

Prediction endpoints are read-only. Data generation and retraining are control operations and therefore require the shared control token. User-supplied training/output paths are constrained to the configured data directory.

### Orchestrator

The Orchestrator provides an explicit `event -> prediction -> optional enforcement` path. It does not perform privileged operations itself. If a prediction requires enforcement, it forwards an authenticated request to the Enforcer.

### Enforcer

The Enforcer is the only component intended to run with elevated privileges. It supports:

- cgroup v2 CPU/memory limits;
- a limited cgroup v1 fallback;
- explicit `SIGKILL` of a validated process.

Before an action reaches the OS, the API contract rejects reserved/non-positive PIDs and malformed resource limits. The service also refuses to target itself or its parent process.

### Dashboard

The Streamlit dashboard reads service status and event history and can invoke local control operations. When `AISEC_CONTROL_TOKEN` is present, its API client automatically attaches the bearer token to requests.

## Trust boundaries

```text
unprivileged observation/classification          privileged control

 Sensor ------------> ML ---------------------+       Enforcer
   |                                           |          |
   +--------------> Orchestrator --------------+--------->|
   |                                                      |
 Dashboard ------------------------------------------------+

             shared AISEC_CONTROL_TOKEN on mutating requests
```

The shared token is defense in depth for a local deployment. It is not intended as an Internet authentication system. There is no TLS or per-user authorization, so network exposure should be handled by a separate hardened layer or avoided entirely.

## Detection and enforcement flow

1. The Sensor samples a process and creates a normalized event.
2. The event is placed in a bounded buffer and optionally exported.
3. If auto-detect is disabled, processing stops there.
4. A cheap pre-filter discards events with no relevant signal.
5. Protected processes, duplicate in-flight PIDs, and recently submitted PIDs are skipped.
6. The Sensor requests an ML prediction.
7. A model `block` recommendation is treated as a detection; explicit rules provide a fallback when appropriate.
8. The Sensor records the detection and sends an authenticated action to the Enforcer when auto-enforcement is enabled.
9. The Enforcer re-validates the target and resource limits before touching cgroups or signals.

This separation is intentional: a detector should not be able to turn malformed event data directly into an unrestricted OS operation.

## Failure behavior

- ML timeouts do not automatically become enforcement decisions; rule fallback may still detect an explicit condition.
- Enforcer failures are recorded in enforcement history instead of being reported as successful blocks.
- The launcher refuses to kill unrelated processes merely because a project port is occupied.
- Unsupported eBPF mode is rejected at request validation instead of partially starting the Sensor.
- Generated model/data paths cannot escape `AISEC_DATA_DIR` through API input.

## Data and model limitations

The repository's model is trained on synthetic examples generated by code in the repository. This is useful for integration testing and demonstrations, but train/test scores can be strongly influenced by how the generator and engineered features are defined. They should not be cited as evidence of endpoint-detection performance on real workloads.

A meaningful next research step would use independently collected, labeled traces and evaluate false-positive/false-negative behavior across hosts and workloads before changing enforcement policy.
